# engine_next auction loader — real Redis capture audit (2026-09-07)

## Scope

This evidence records a read-only run of the exact legacy
`IntradayDataHub.load_auction_snapshots()` path against real Redis capture
files produced by the production audit tooling on `cobra-ion`. The capture
files were not generated by the new core and were not hand-authored fixtures.

The probe ran the legacy loader behind the existing fail-closed `GuardRedis`
and did not construct `IntradayContextBuilder`, consume RabbitMQ, access
TDengine or network connectors, invoke recovery, or write Redis/TDengine.

## Interpretation boundaries

This proves that the narrow legacy Redis snapshot reader can consume a real,
non-empty captured production projection without attempting writes. It does
not prove:

* live Redis currently retains non-empty historical 0920/0924/0925 keys;
* a 0920/0925 row was produced by the same runtime batch or Rabbit delivery;
* the capture is an immutable full-universe snapshot;
* the old zero-fill or `summary.ts` behavior is a valid new-core contract;
* Redis projection is semantically equal to `stock_tick_v2` or
  `auction_snapshot_v2` without an authority-aligned comparison.

The old loader's `redis_keys_written` result field remains reported by the
probe as `legacy_keys_reported`; it is not treated as a write claim.
